# API 호출 검토·최적화 · 2026-11-05

프런트에서 불필요하게 반복하던 조회를 줄였다. **동일한 개발 모드·룸 3개·모의 API 시나리오에서 첫 로그인/홈 진입은 18회 → 10회, 즉시 홈 복귀는 7회 → 0회**였다. 실서버의 현재 룸 1개 계정에서도 첫 진입 8회·즉시 홈 복귀 0회와 정상 응답을 확인했다. [상태·요청 수 기록](API_CALL_OPTIMIZATION_2026-11-05.json) 참고.

측정은 브라우저의 `/api/backend/*` 요청 수다. 프록시가 같은 요청을 백엔드 `/api/*`에 전달하는 단계는 별도 기능 호출로 중복 집계하지 않았다. 최초 집계에는 익명 refresh, 약관, 로그인도 포함한다. 모의 API 수치를 실서버 전체 트래픽·응답 시간·요금 절감률로 해석하지 않는다.

## 확인한 원인과 수정

| 원인 | 영향 | 적용한 수정 |
|---|---|---|
| 로그인 loadUser 직후 HomePage가 refreshHome → loadUser 반복 | `/me`, `/home`, 일정, 아바타, 룸 상세 N개를 두 번 조회 | 인증 초기 로드 공유, 홈 조회 분리, 짧은 메모리 캐시 재사용 |
| 홈에 돌아올 때마다 전체 계정 자료 갱신 | 변경되지 않은 `/me`, `/avatars`와 모든 룸 상세까지 반복 | 홈·일정과 만료된 룸만 조회. `/me`, `/avatars`는 홈 복귀에서 제외 |
| 동일 GET의 동시 요청이 각각 전송됨 | StrictMode의 약관·리포트 중복 및 겹친 화면 조회 | ApiClient가 같은 인증 세대·공개/보호 구분·경로의 진행 중 GET만 공유 |
| 약관을 모든 최초 URL에서 조회 | 공부·리포트·비밀번호 재설정 진입에도 사용하지 않는 약관 조회 | 약관은 `/login` 진입에서 로드 |
| 화면 복귀 때마다 heartbeat 전송 | 짧은 탭 이동에도 주기 요청 외 전송 | 최근 성공이 1분 이내이면 복귀 heartbeat 생략. 1분 정기 전송과 명시적 재시도는 유지 |
| 리포트 로더의 중복 실행 | 이미 가진 종료/리포트를 다시 요청할 가능성 | 서버 리포트가 메모리에 있으면 반환. 새로고침 시 GET은 동시 1회 |

## 캐시·무효화 기준

| 자료 | 메모리 재사용 기간 | 갱신 기준 |
|---|---|---|
| 홈 | 10초 | 다음 홈 조회에서 만료 확인. 공부 시작/이어하기/종료 직후 무효화 |
| 일정 목록 | 10초 | 다음 홈 조회에서 만료 확인. 일정 저장 직후 무효화·화면에는 생성 응답 즉시 추가 |
| 룸 상세 | 30초 | 홈 동기화에서 만료 확인. 해당 룸의 공부 시작/이어하기/종료 직후 무효화 |
| 아바타 목록 | 5분 | 계정 자료를 다시 로드할 때 만료 확인. 일반 홈 복귀에서는 조회하지 않음 |
| 약관 | 별도 결과 캐시 없음 | 로그인 경로 진입 시 조회. 동시 GET만 공유 |
| 종료 리포트 | 현재 계정의 앱 메모리 기록 | 종료 응답 재사용. 전체 새로고침 시 다시 조회 |

기간은 자동 폴링 주기가 아니다. 가만히 있는 홈에서 주기적으로 요청을 만들지 않고, 다음 조회 시 만료된 항목을 갱신한다. 다른 기기에서 바뀐 자료는 이러한 다음 조회까지 바로 표시되지 않을 수 있다. 사용자가 실행한 전체 reload는 홈·일정 캐시를 무효화한다.

- 로그인·로그아웃·인증 해제 때 계정별 캐시를 교체한다. 이전 계정 요청의 늦은 응답을 새 계정에 게시하거나 새 캐시에 채우지 않는다.
- 실패한 요청은 캐시하지 않는다. 동일 경로의 후속 재시도는 다시 서버에 요청한다.
- 저장 성공 이후의 조회는 저장 이전에 시작한 GET에 합류하지 않는다. 무효화된 요청의 늦은 결과가 새 캐시를 덮지 않도록 한다.
- 일정 변경·세션 변경의 버전을 확인해, 변경 이전에 시작한 홈/일정 응답이 새 상태를 덮는 것을 막는다.
- POST/PATCH, 요청별 AbortSignal이 있는 GET, 공개/보호 구분이 다른 GET은 동시 요청 공유 대상이 아니다. 쓰기 요청을 캐시하거나 임의 재시도하지 않는다.
- HTTP/브라우저/공용 서버 캐시는 계속 no-store다. 추가 캐시는 현재 앱 메모리에만 있고, 토큰·응답을 저장소에 새로 보관하지 않는다.

## 같은 조건의 브라우저 결과

| 시나리오 | 수정 전 | 수정 후 |
|---|---:|---:|
| 로그인 화면 → 로그인 → 홈, 룸 3개 | 18회 | **10회** |
| 바로 룸 상세 → 홈 | 7회 | **0회** |
| 홈/일정의 10초가 지난 뒤 홈 복귀, 룸 캐시 유효 | 7회 | **2회**: 홈·일정 |
| 룸의 30초도 지난 뒤 홈 복귀 | 7회 | **5회**: 홈·일정·룸 3개 |
| StrictMode 리포트 새로고침의 리포트 GET | 2회 | **1회** |

개발 StrictMode에서 나타나는 약관·리포트 중복은 개발 모드 특성도 원인이다. 로그인 완료 후 홈 전체를 다시 읽던 동작과 홈 복귀의 과도한 묶음 조회는 프로덕션에서도 적용되던 코드다. 수정 전 리포트 2회는 앞선 실계정 점검의 Network에서도 확인했다. 최초 18회와 즉시 복귀 7회는 이번 수정 전후에 동일 모의 API 조건으로 측정했다.

추가 브라우저 검증은 모의 응답과 가상 시계로 수행했다.

- 일정 저장 후 홈 복귀: 다른 유효 캐시를 유지하면서 일정만 1회 재조회.
- 캐시가 아직 유효한 짧은 세션 종료 후 홈 복귀: 홈과 해당 룸만 재조회. `/me`, `/avatars` 재호출 없음.
- 공부 중 65초 경과: heartbeat 1회, `studySeconds/presentSeconds=65/65`.
- 휴식 60초 경과: heartbeat 유지, 누적 값은 동일한 65/65로 휴식 제외.
- 시작 직후와 heartbeat 직후 각각 visibilitychange 5회: 추가 heartbeat 0회.
- 종료 직후: 종료 응답으로 리포트 표시, report GET 0회. F5 뒤에는 report GET 1회.
- 로그아웃 뒤 다른 모의 계정 로그인: 아바타·일정·룸 새 요청과 새 계정 프로필 표시 확인.

실서버에서는 기존에 제공받은 계정으로 로그인·프로필/홈/일정/아바타/룸 조회와 상세 화면·홈 복귀·로그아웃을 확인했다. 정상 200·로그아웃 204였으며 최초 익명 refresh 401은 예상된 응답이다. 이번 최적화 검증으로 실제 일정·공부 세션·비밀번호를 변경하지 않았다.

## 유지한 호출과 추가 개선 후보

공부 중 250ms 관측 샘플과 1초 화면 타이머는 로컬 계산이며 매번 API를 보내지 않는다. 안정적인 공부 상태에서는 1분 heartbeat가 기본 요청이다. 상태 변경은 events 저장 후 eventId에 대한 reaction, 사용자 대화는 messages를 호출한다. 상태 저장과 반응은 계약상 역할이 달라 두 API를 임의로 하나로 줄이지 않았다. AWAY 반응의 단계 진행도 유지했다. refresh의 동시 1회 처리·401 후 한 번 재시도도 유지한다.

| 후보 | 남은 이유·검토 방향 |
|---|---|
| 최초 홈의 룸 상세 N건 선조회 | 아직 `1+N` 구조다. 홈의 설명 검색과 화면의 관계·성격 정보가 상세 응답에 의존한다. 페이지별 지연 조회와 로딩 상태를 설계하거나 백엔드 home 요약 필드를 확장하면 최초 N건도 줄일 수 있음 |
| 최초 리포트/카드에서도 홈·일정·아바타를 로드 | 전역 계정 초기화 구조가 남아 있음. 화면별 데이터 의존성을 분리하면 리포트만 필요한 진입을 더 가볍게 만들 수 있음 |
| 같은 계정의 여러 탭에서 동시에 공부 | 요청 공유는 현재 탭 안에서만 적용. 여러 탭의 세션 제어는 별도 정책·백엔드 멱등성 확인이 필요하며 단순 전역 캐시로 대체하지 않음 |
| 실제 서버 부하·응답 시간 | 이번 수치는 프런트 요청 수. DB 조회·네트워크 용량·서버 처리 시간은 별도 서버 계측 대상 |

## 검증

전체 단위 테스트 **198개 통과**, ESLint·타입 검사·프로덕션 빌드·`git diff --check` 통과. 새 검사는 GET 동시 공유, 쓰기·취소·인증 구분, 계정 전환, 실패 재시도, 저장 이후 읽기, TTL 경계, 무효화와 늦은 응답을 포함한다. 브라우저 검사에서는 캐시 만료·쓰기 무효화·heartbeat·계정 전환·리포트 복구를 통과했다. 기존 Vite 설정의 확장자 없는 서버 import에 대한 향후 호환성 경고는 남아 있다.
