## 1. 확인된 이벤트 종류

| 구분 | 서버 코드 | 의미·전송 조건 |
|---|---|---|
| 상태 변화 | `FOCUS` | 공부 시작·휴식 후 다시 공부. 다음 상태까지 유지 |
| 상태 변화 | `AWAY` | 자리 비움. 다음 상태까지 유지 |
| 상태 변화 | `RETURN` | 자리 비움 후 돌아옴. 다음 상태까지 유지 |
| 상태 변화 | `BREAK` | 쉬는 시간·일시정지. 다음 상태까지 유지 |
| 순간 동작 | `DROWSY` | 졸음 1회 |
| 순간 동작 | `YAWN` | 하품 1회 |
| 순간 동작 | `WAVE` | 손 흔들기 1회 |
| 순간 동작 | `HEAD_TURN` | 고개 돌림 1회 |

핸드폰은 이 문서의 순간 동작 목록에 없다. `PHONE` 같은 서버 코드를 임의로 만들지 않는다. 현재 프런트의 핸드폰 감지 배지는 로컬 기능으로 남는다.

### 상태와 순간 동작의 차이

- 상태 변화는 공부·휴식·자리 지킴 시간 계산에 반영된다. 상태가 실제로 바뀔 때 기록한다.
- 순간 동작은 기존 공부 상태와 시간 계산을 바꾸지 않으며 호감도 변화는 항상 0이다.
- 같은 순간 동작의 반응은 **1분에 한 번**만 허용한다. 다른 종류 사이에 공통 20초 제한을 두라는 규칙은 새 문서에 없다.
- 순간 동작은 휴식 중 무시한다. 현재 앱에 없는 일시정지 UI를 새로 추가하라는 요구로 해석하지 않는다.
- 이 문서에는 새 얼굴 감지 임계 시간이 없다. 기존 API 자료의 연속 10초 AWAY 기준과 프런트의 졸음·하품·고개 돌림·손 흔들기 감지 기준은 별도 기준으로 유지한다.

## 2. 새 호감도 정책

| 상황 | 새 정책 |
|---|---|
| 첫 만남 | 기본 호감도 50, 관계 2단계. 서버가 초기화할 값 |
| 연속 출석 | 연속 출석 조건을 충족한 첫 공부 시작에 +1. 2일째부터 적용 |
| 자리 비움 시작 | 즉시 감점하지 않음 |
| 1분 이내 복귀 | 감점 없음. 정확히 60초도 감점 조건에 해당하지 않음 |
| 1분 초과 후 복귀 | 복귀 시 실제 자리 비움 시간을 계산해 -1 |
| 하루 자리 비움 감점 | 최대 -3 |
| 복귀 자체 | 별도 가산 없음 |
| 휴식·다시 공부·순간 동작 | 0 |

출석·일일 상한·호감도 확정은 백엔드 책임이다. 프런트는 초기 50을 더미로 채우거나 자체 +1/-1 적립을 하지 않고, 서버 확정 응답을 반영한다. 출석 날짜 경계·중복 세션 처리도 서버 계약에 맞춘다.

기존 `API관련/`에는 첫 FOCUS +5 예시, AWAY 즉시 -1, RETURN +1이 있었다. 새 정책 적용 시 이 예시를 실제 규칙으로 사용하면 안 된다. 자리 비움 시간과 공부 레벨은 호감도와 별도로 유지한다.

## 3. 순간 동작의 대사 선택

순간 동작에는 **LLM 생성 대사 대신 사전 작성된 대사**를 사용한다.

| 관계 단계 | 호감도 범위 |
|---|---|
| 1단계 | 0~29 |
| 2단계 | 30~69 |
| 3단계 | 70~89 |
| 4단계 | 90~100 |

1. 현재 호감도에 해당하는 단계의 대사를 선택한다.
2. 해당 단계가 비어 있으면 하위 단계의 대사로 대체한다.
3. 같은 단계에 여러 대사가 있으면 순서대로 순환한다.
4. 같은 공부 시간 안에서 동일 대사가 연속으로 나오지 않게 한다.
5. 같은 동작은 1분에 한 번만 반응한다.

대사 작성 표는 **동작 4개 × 단계 4개 = 16칸**이며, 각 칸에 대사 1~3개와 표정 1개를 작성한다. 표정 목록은 웃음·찡그림·화남·삐짐·수줍음·집중이다. 제공된 표는 **모든 칸이 비어 있다**. 원문의 하품 예시는 정책 설명용이며, 현재 채린 MVP의 확정 대사 목록과 구분한다.

선택 가능한 하위 단계도 전부 비었을 때의 응답, 선택지가 한 문장뿐인 경우의 연속 중복 방지, 중복 방지의 범위가 동작별인지 전체 발화인지, 표정 이름과 실제 모델 파일의 매핑은 후속 계약 확인이 필요하다. 실제 문구를 프런트에서 임의 작성해 API 성공처럼 표시하지 않는다.

원문 비교표는 상태 변화도 상황별 사전 작성 대사로 설명한다. 별도 5-5절은 상태 변화에 관계 단계별 대사를 추가하는 기능을 후속 확장으로 다룬다. 기존 상태 반응의 LLM 경로도 바뀌는지와 단계별 대사 적용 범위를 백엔드 반영 시 함께 확인해야 한다.

## 5. 배포 API 확인과 남은 계약

최신 전체 점검에서는 `RoomDetail.bannerUrl`만 추가되었고 아래 순간 동작·사전 대사 계약은 그대로다. 상태 API는 실제 FOCUS 저장 201과 reaction 200을 확인했다. [전체 API 점검표](API_AUDIT_2026-11-05.md)를 참고한다. 이 성공을 순간 동작 새 정책의 배포 확인으로 확대하지 않는다.

정책 검토 당시 [배포 Swagger](https://backendlab-production-3052.up.railway.app/swagger-ui/index.html#/)와 [OpenAPI](https://backendlab-production-3052.up.railway.app/v3/api-docs)는 기존 스냅샷과 동일했다. 후속 17개 API 재점검에서 [현재 스냅샷](BACKEND_OPENAPI_2026-11-05.json)을 갱신했으며, 변경은 카카오 요청의 약관 버전 필드 제거 한 곳이다. 아래 상태·순간 동작 계약에는 변화가 없다.

- `EventRequest.type`은 enum 없는 string이다.
- `/events` 설명에는 졸음·하품·손 흔들기·고개 돌림 감지가 언급되어 있다.
- `/events/{eventId}/reaction`은 여전히 **LLM 대사 생성**으로 설명되어 있다.
- 관계 단계별 사전 대사 데이터와 그 조회/반응 계약은 OpenAPI에 없다.

사용자가 백엔드 **반영 예정**임을 확인했으므로, 현재 네 상태 이벤트 연결은 유지하고 순간 동작의 실제 API 전송은 대기한다. 백엔드 반영 뒤에는 다음 항목을 확인한다.

| 확인 항목 | 필요한 내용 |
|---|---|
| 이벤트 경로 | 같은 `/events`가 네 순간 동작도 받는지, 상태 계산과 분리해서 저장하는지 |
| 반응 경로 | 같은 `/reaction`이 사전 대사를 반환하는지, 별도 경로/응답이 추가되는지 |
| 무시·제한 응답 | 휴식 중·1분 제한·대사 없음 시 HTTP 상태, eventId와 characters의 값 |
| 호감도 응답 | 순간 동작 delta=0, 복귀 시 감점·하루 최대 -3·연속 출석 +1 적용 |
| 대사·표정 원본 | 채린의 실제 16칸 대사와 표정 데이터, 선택·순환을 담당할 서버 동작 |
| 프런트 검증 | 순간 동작이 상태·시간·복귀 수·AWAY 반복 반응을 바꾸지 않음. 반복 감지·휴식·늦은 응답·재전송 처리 |

이 검토에서는 실행 코드·호감도 계산·API 전송 대상을 변경하지 않았다. 이번 확인으로 순간 동작 코드 네 가지는 확인되었고, 대기 사유는 **코드 미확인**에서 **백엔드 새 정책 반영·응답 계약 확인**으로 바뀌었다.
