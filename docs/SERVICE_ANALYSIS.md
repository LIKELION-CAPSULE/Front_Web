# 서비스·와이어프레임 분석

> 이 문서는 최초 웹 토대 단계의 분석입니다. 이후 화면 전체를 더미 상태로 연결한 범위는 [화면 지도](FIGMA_SCREEN_MAP.md)와 [구조 문서](FRONTEND_ARCHITECTURE.md)를 참고하세요. UI 데모의 임시 계산·문구가 공식 정책 확정을 의미하지는 않습니다.

분석일: 2026-10-26. 근거: [서비스 기획 정리](CAPSULE_서비스_기획_정리.md), [Figma 와이어프레임 페이지](https://www.figma.com/design/HpoEbOqfoDUwPq4zvYa6LL/?node-id=682-172). 아래의 ‘제안’은 구현을 위한 해석이며 확정 기획·API 계약이 아닙니다.

## 1. 서비스의 중심

CAPSULE은 캐릭터와 함께 공부를 시작하고, 함께한 공부가 관계와 기억으로 남아 다시 방문하게 만드는 서비스입니다. 집중 감지 자체보다 **감지 → 캐릭터의 자연스러운 반응 → 공부 복귀 → 관계 축적**의 연결이 제품의 차별점입니다.

주 사용자는 노트북으로 공부하는 대학생이며, 특히 경쟁·순위보다 동반감과 재미를 선호하는 사용자입니다. 예약이나 사람 매칭 없이 공부를 시작할 수 있어야 하고, 정상적인 독서·필기를 방해하는 오반응은 줄여야 합니다.

기본 루프는 다음과 같습니다.

```text
첫 방문: 로그인 → 아바타 → 홈 → 룸 상세 → 카메라 확인
매 세트: 세트·등급 선택 → 공부 50분 → 휴식·대화 10분
마무리: 종료 결과 → 캡슐 카드·다음 약속 → 기록·관계 → 재방문
```

UI에서 중요한 구분은 첫 방문/재방문, 룸/캐릭터, 공부/휴식, 카메라 관측 가능/불가, 검증 시간/단순 경과 시간입니다. 이를 하나의 ‘집중 여부’나 하나의 캐릭터 상태로 합치면 이후 정책 변경이 어려워집니다.

## 2. 제품 범위와 사업 구조

기획의 수익 원칙은 ‘공부는 무료, 관계는 프리미엄’입니다. 무료 공부를 끝까지 경험한 뒤 대화·음성의 가치가 느껴져야 유료 전환도 설득력을 가집니다. 따라서 첫 세션 완료와 다음 방문을 먼저 검증하는 것이 합리적입니다.

| 구분 | 핵심 내용 | 프론트엔드에 미치는 영향 |
|---|---|---|
| 무료 경험 | 공부·기본 반응·복귀 칭찬 | 결제 여부와 공부 시작 가능 여부를 분리 |
| 유료 경험 | 대화 품질·기억·음성·특별 연출 | 세션 등급을 명시하고 잔액·권한은 서버 결과 사용 |
| 관계 성장 | 원본 원칙은 유효 공부 시간으로만 증가 | 결제·선물 클릭을 호감도 증가와 연결하지 않음 |
| UGC | 룸 제작·검수·공개·정산 | 초기 공식 룸 탐색과 분리, 이번 기반에 편집 도구 추가 안 함 |
| 유지율 | 함께한 기억·약속·해금 | 빈 상태/첫 방문과 실제 기록이 있는 상태를 따로 설계 |

매출, 마진, 감지 정확도 목표와 원본의 기기 성능은 기획 가정 또는 특정 환경 측정입니다. 이번 작업에서 시장·수익·감지 성능을 검증하지 않았습니다.

## 3. 화면에서 읽히는 정보 구조

와이어프레임은 화면 오른쪽의 메모에서 정보의 생성·변경·기록·읽기를 나눕니다. 이는 프론트엔드의 데이터 경계를 정하는 근거이며 DB 테이블을 확정했다는 뜻은 아닙니다.

| 정보 묶음 | 예시 | 권장 책임 |
|---|---|---|
| 서비스 콘텐츠 | 룸 설명·참여 캐릭터·모션·대사 | 콘텐츠 API와 렌더 UI 분리 |
| 사용자 설정 | 이름·아바타·배경·카메라 설정 | 계정 설정과 브라우저 장치 상태 분리 |
| 세션 | 룸·참여자·시작/종료·공부/휴식·등급 | 단일 세션 상태 전이, 서버 마감과 대조 |
| 집중 이벤트 | 집중·이탈·자리 비움·복귀·오탐 피드백 | 원본 영상 없이 상태 변화만 전달 |
| 관계·기억 | 캐릭터별 시간·관계 변화·해금·시험·약속 | 서버를 기준으로 조회, 변경 이유 보존 검토 |
| 크레딧 | 차감·충전·패스·중간 승급 | 원장과 승인 결과를 서버가 관리 |

특히 한 룸에 여러 캐릭터가 있으므로 `StudyRoom.characters`를 배열로 둡니다. 사용자 공부 시간이 50분이고 캐릭터가 3명이라고 사용자 총 공부 시간을 150분으로 합산하면 안 됩니다. 캐릭터별 동반 시간 산정은 별도 정책입니다.

## 4. 문서와 Figma 사이의 확인·결정 항목

충돌을 최신안이라는 이유만으로 덮어쓰지 않았습니다. 이번 코드에서는 아래 정책을 실행하지 않습니다.

| 주제 | 원본 문서 | Figma에서 확인한 내용 | 구현 전 결정 |
|---|---|---|---|
| 공부 중 대화 | 공부 중 자유 AI 채팅은 열지 않음 | S08 미니 채팅·빠른 답장, 타이머 유지, 베이직 일 3턴과 공유 | 허용 범위·요금·집중 적립 중단 여부·응답 길이 |
| 관계 증가 | 유효 공부 시간으로만 증가 | S11 메모는 완료·연속 방문·이벤트도 정책 후보로 언급 | 공부 외 이벤트를 관계에 반영할지, 원칙 우선순위 |
| 카메라 초기 확인 | 세션 시작 5초 보정 계획 | S05는 첫 회만, 재방문은 설정 재사용 | 권한/장치 재획득과 보정 분리, 카메라·각도 변경 시 재점검 |
| 카메라 없는 모드 | 존재하나 적립·검증 제한 미정 | 감지 방식을 카메라/마우스로 기록 | 관측 불가 표시, 인정 시간·호감도 정책. 마우스 입력만으로 공부 증명 불가 |
| 휴대폰 반응 | 일반 3초, 데모 보수적 5초 | S06의 임계값은 [N]초 | 데모/출시 기준과 쿨다운 확정 |
| 하루 경계 | 별도 확정 없음 | 대화는 새벽 5시 초기화, 기록 보드는 하루 정의 미정 | Asia/Seoul 등 기준 시간대, 일일 통계·대화·패스 경계 일치 여부 |
| 중간 등급 올리기 | 세트 시작에 선택 | S06-e에서 이미 낸 금액을 뺀 차액 결제 | 재시도·중복 차감·패스·진행 중 환불 정책과 원장 계약 |
| 보이스 가격 | 이름 부르기 100크레딧 예시 | S11-b 선택 상품 예시는 300크레딧 | 가격표와 상품 ID 확정, 클라이언트 가격을 승인 근거로 쓰지 않음 |
| 룸 인원 | 캐릭터와 함께 공부 | S04/S06은 1:1 또는 1:3, 크게 보기 가능 | 룸에 속한 캐릭터와 선택한 동반자 구분, 저사양 상한 |
| 초기 아바타 | 기본 MVP의 필수 경험에 비해 부가 범위 | S02의 헤어·의상·외모, 별도 재활용수거함의 배경 업로드 화면 | 11/7 베타에서 기본 아바타만 쓸지 결정. 수거함 화면은 활성 요구사항으로 취급하지 않음 |
| 저장·조회 로그 | 명시적 MVP 필수 아님 | S03 메모에서 MVP 제외 | 카드의 저장 UI는 비활성화, 행동 로그·개인화 수집 안 함 |
| 종료/북극성 지표 | 25분 첫 완료 KPI, 기본 세트는 50분 | S10 이용일 중심, 비정상 세션 별도 표시 | 최소 인정 시간·첫 세션 완료 정의·자정 경계·비정상 마감 합의 |

그 밖의 원본 미확정 사항은 원본 15절에 보존되어 있습니다. 구매로 관계·엔딩을 열 수 있는 듯한 해석은 원본 원칙과 충돌하므로 콘텐츠 해금 조건과 유료 음성 상품을 구분해야 합니다.

## 5. 구현 우선순위 제안

| 단계 | 목표 | 완료 판단 |
|---|---|---|
| 현재: 웹 기반 | 구조·공통 UI·탐색 화면·문서 | 설치/타입 검사/린트/빌드, 홈→상세·메뉴·잘못된 주소 동작 |
| 1: 세션의 수명 | 카메라/권한/중단, 50+10 타이머, 종료·복구 | 거부·장치 없음·탭 이동·중단 후에도 영상과 시간이 잘 정리됨 |
| 2: 동반 경험 | 단일 캐릭터 렌더, Worker, 반응·‘아니야’ | 독서/필기 오탐 확인, 반응 후 기본 모션 복귀, 과도한 개입 방지 |
| 3: 결과·재방문 | 서버 기록, 집중 리포트, 관계 조회 | 실제 세션 결과와 오늘/주간/캐릭터 합계가 일치 |
| 4: 대화·사업 기능 | 인증, 휴식 대화·기억·음성, 등급·크레딧 | 세션/계정/원장 API와 실패·재시도·취소 정책 검증 |
| 이후 | 1:3 최적화, 아바타 편집, 공유·약속, UGC·정산·현지화 | 각 기능의 수요·성능·운영 기준 합의 |

카카오/구글 인증이 필요한 단계부터 실제 인증과 서버 사용자 식별은 해당 기능에 앞서 연결합니다. 위 순서는 기술적 수직 슬라이스 제안이며 인증 없이 실제 개인 기록·유료 기능을 서비스한다는 뜻은 아닙니다.

11/7 베타와 12월 출시는 원본 계획입니다. 2026-10-26 현재의 실제 개발 진척은 이 저장소만으로 확정할 수 없으므로 위 목록을 일정 달성의 보장으로 사용하지 않습니다.

## 6. 기술 설계에서 유지할 경계

- 카메라 스트림은 장치 수명 관리에 두고, 권한 요청은 명시적 사용자 행동 뒤에 수행합니다. 종료·경로 이탈·비동기 권한 응답 뒤 스트림 해제도 다뤄야 합니다.
- 얼굴 좌표와 프레임은 Worker/브라우저 안에 남기고, 상태 라벨·시간 요약만 API 모델에 포함합니다. 브라우저 단독 계산을 검증된 시간으로 표시하지 않습니다.
- 감지의 ‘판단 불가’를 ‘집중’으로 합치지 않습니다. 숨김 탭, 추적 끊김, 정상 필기, 보이지 않는 휴대폰을 각각 고려합니다.
- 캐릭터 렌더러와 반응 정책을 분리합니다. 여러 캐릭터를 렌더링하더라도 감지 파이프라인을 중복 생성하지 않습니다.
- 가격·잔액·호감도·해금·시간 인정은 서버 계약이 정해진 뒤 연결합니다. 현재 샘플 데이터에 확정되지 않은 API 주소나 가짜 성공 흐름을 만들지 않았습니다.

## 7. 이번 작업의 결론과 경계

첫 방문 홈과 룸 상세를 실제 구조로 만들고, 재사용 UI·라우팅·디자인 값·샘플 데이터 읽기를 분리했습니다. 기획 주석과 제품 UI도 구분했습니다. 기록·관계·크레딧 경로는 준비 상태이며, 세션 엔진과 카메라를 구현한 상태는 아닙니다.

이번 기반은 다음 단계에서 기능 하나씩 연결하기 위한 출발점입니다. 실제 사용자 데이터, 감지 성능, 사업 수치와 Figma 밖의 확정 요구사항은 검증하지 않았습니다.
